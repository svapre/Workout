# Plan Family Review Brief

## What this packet is for
This packet is for a thorough review of the full **plan family**:
- active-plan entry/detail/study
- blueprint entry/detail/study
- blueprint editor
- stage editor

## What the review should judge
Judge the current plan family against the newer stage-object direction:
- compact stage cards are goal-first
- Study owns process
- detail pages own the local decision
- mobile runtime/study clarity matters more than desktop polish
- editor screens should author the same model that Study explains

## Current direction
- `Active Plan Detail` is the day-to-day runtime owner surface.
- `Blueprint Detail` is the adoption/decision surface.
- `Study` should read as a path with one selected stage script, not stacked chapter cards.
- `StageCompact` should explain what the stage is trying to achieve, not how it works.
- Ordered routine/rest process belongs in Study and deeper detail.
- Phone runtime/study surfaces are primary. Phone editors are secondary utility surfaces.

## What changed recently
1. Compact plan verbs were normalized toward clearer destination labels like `View plan`, `Study plan`, `Study stage`, `View blueprint`, and `Create active plan`.
2. Detail-page path previews were lightened so they stop repeating the same current/opening-stage explanation already owned by the main module above.
3. Mobile Study was pushed further toward `selected node + attached script` instead of heavy chapter cards.
4. Blueprint Study now has stronger visual separation from Active Plan Study.
5. The contract stack was aligned with `STAGE_SURFACE_CONTRACT.md` and `STAGE_STEP_CONTRACT.md`, so stage compact cards are no longer judged against the retired strip-everywhere model.

## Important constraints for this review
- Do **not** assume the older plan-redesign direction is still correct if it conflicts with the newer stage-object contracts.
- Do **not** ask compact stage cards to inline full routine/process detail.
- Prefer fixes that strengthen one reusable `StageNode / Study script` system across the whole plan family.
- Treat phone editor polish as lower priority than phone runtime/study clarity.

## What this review should decide
1. Is the whole plan family now coherent enough to freeze?
2. Are the remaining problems mostly in stage-node grammar, mobile Study behavior, or entry-card comparison?
3. Which screens are ready for beautification now?
4. Which screens still need one last framework pass?
