# UI Language Review Brief

Purpose: review the app's naming, compact-view behavior, and portrait-phone-first hierarchy across the current Exercise, Routine, Plan, and History surfaces.

## Why This Review Exists
- The app has a stronger structure now, but compact mobile views can still feel too desktop-derived.
- Some compact cards still explain too much before expansion.
- Some labels are still too internal, poetic, or ambiguous for first-time users.
- The next phase should standardize naming and compact-view responsibilities across the whole app, not only plans.

## Current Direction Being Tested
- Portrait phone is the primary design truth.
- Compact views explain what the item is.
- Detail/study views explain why and how it works.
- Action labels should reveal destination or outcome.
- Static badges, selection controls, navigation rows, and navigation chips should be visually distinct.
- Routine/stage labels in compact contexts should be user-facing, not just internal titles.

## What To Look For

### 1. Compact clarity
- Can a user tell what a card/node/row represents without reading a paragraph?
- Do compact surfaces become mini detail pages?
- Are cards too variable in height for scan-first mobile use?

### 2. Naming clarity
- Are labels explicit enough for a first-time user?
- Are internal names being shown without translation in compact contexts?
- Do action labels tell the user where they are going?

### 3. Mobile-first hierarchy
- Do the phone screenshots feel like the source design, or like compressed desktop cards?
- Does expansion feel attached to the selected item?
- Is the selected state obvious on phone without unnecessary secondary controls?

### 4. Cross-app consistency
- Do Exercise, Routine, Stage, Blueprint, and Active Plan feel like one family?
- Do compact, detail, and study responsibilities stay consistent across the hierarchy?
- Are there any places where the app invents one-off previews instead of following the shared rules?

## Desired Outcome
We want a critique that helps us decide:
- whether the new contracts are strong enough
- which screens still violate them
- and where the next narrow framework pass should go before beautification
